### 当时的产品结果

阶段 4：调用其他 AI 工具中的一个原生完整场景：

> 我说清要改什么，看见真实目标项目和任务草稿，确认后让她在后台执行；我收起面板继续工作，回来仍能看到这件事的真实结果，并决定是否采用。

## 产品管理规则

2026-09-26，响应用户对开发偏移的反馈。这些规则用于约束实际工作，不新增管理工具或另一份任务清单。

1. **一次明确一个产品交付。** 可以并行拆实现、研究和验证，但说明它们如何服务该交付。用户另行授权的实验单独标记，不悄悄取代主线。
2. **开工前说清结果。** 用一句用户场景写出本次可见变化、通过条件和不做什么；小修复引用当前契约即可，不重复造文档。
3. **区分授权与完成。** 状态使用候选、待开始、进行中、阻塞、待用户验收、已验收或停放；已有代码/构建/原型只是证据备注。研究结束不等于采纳方案，接入成功不等于产品体验通过。
4. **研究必须帮助决定。** 开始前说明要解决哪项取舍、用什么有界试验、看到什么就能结束。能实际试的先试；结论应是采用建议、保留候选或不适合，并交代依据。新参考先归入相关候选，不自动安装、授权或开新实现。
5. **遇阻碍先判断是否挡住用户结果。** 在已授权范围内主动验证替代路径；不要围绕一个可替换工具无限排障。替换工具时保留目标、权限和回执，配置与账号变化必须明示。
6. **改变范围时显式说明代价。** 用户的新要求优先；主代理指出它是补充当前交付、单独实验还是改变主线，并说明哪项会延后。方向决定回写 `PRODUCT.md`，优先级决定回写本页，记录理由和取代项；建议仍标为建议。可逆的实现细节由主代理负责，方向、体验取舍和新增权限由用户决定。
7. **每轮收尾更新同一个入口。** 汇报用户可见变化、真实证据、尚未完成的部分、下一步；同步本节状态。不能把内部小步、子代理结束或未验证建议写成产品完成。

当前管理是否有效，要看后续工作能否一直回答：**正在完成哪个用户场景？这次工作为什么必要？什么证据算通过？此刻明确不做什么？** 文档整理本身不证明偏移问题已经消失。

## 目标架构

```
                    用户（语音 / 快捷键 / 以后的唤醒词）
                                   │
                    ┌──────────────▼──────────────┐
                    │     Her.app（Swift，唯一大脑）  │
                    │  语音会话 · 人格 · 记忆 · 技能   │
                    │  任务协调 · 回执 · 确认 · 验证   │
                    └───┬──────────────┬───────────┘
          桌面操作        │              │  Chrome 扩展（本机 WebSocket，Origin 认证）
  AX / OCR / YOLO 感知   │              │
  WorkflowRunner → CUA                            │     ┌────────▼─────────┐
                         │     │  Her 浏览器扩展   │  在本仓库新建，设计参照研究文档
                         │     │ 只做控制面：DOM   │  CDP 用最小集合；标签页归属；

                         │     │ 截图、教学录制    │

```

原则：整个系统由 Her 统一协调。2026-09-26 用户明确：共同上下文、授权、任务状态和回执由 Her 掌握，桌面操作与外部 Coding Agent 分开执行。上图描述桌面操作与浏览器扩展部分；Coding Agent 经现有独立委托执行器运行，不进入桌面点击引擎。扩展和辅助进程只负责感知和执行，不做另一套对话决策；不引入第二个推理运行时。当前已有能力与尚未统一的部分见[架构总览](architecture/README.md)。
