# Provider modes, onboarding and product identity

Part of the [architecture overview](README.md). Moved verbatim from `AGENTS.md` on 2026-09-23.

The shipped product identity is now **Her** (`com.yishuziyu.her`) and local development uses Personal Team `87DM76C54G` with Apple Development signing. The repository, source folder, Swift module and many internal type names still use the historical `TipTour` namespace during migration. Do not perform a cosmetic whole-codebase rename while product/runtime consolidation is still in progress.

macOS 14.2+ menu bar-only SwiftUI/AppKit app (`LSUIElement=true`). Two provider modes ship on `main` — `jev` and `stepfun`. Gemini was removed on 2026-09-25: a stored `gemini` choice restores as `stepfun` (`TipTourMode.restored`), so those users land on voice and the panel asks for the StepFun key; the old Gemini Keychain item is left untouched. StepFun playback goes through `TipTour/Voice/RealtimeAudioPlayer.swift` (formerly `GeminiLiveAudioPlayer`).

- **Gemini realtime**: Ctrl+Option toggles a voice session. Audio and optional screenshots go directly to Gemini using the user's Keychain key. One tool per user turn: a single desktop workflow action or the existing Apple Notes convenience action.
- **StepFun realtime voice**: Ctrl+Option runs a full-duplex voice session. `response.audio.delta` from that same Realtime session is the only playback source; interruptions clear queued audio and pending actions. The realtime model receives **no direct image input**. `describe_screen` passes the locally captured image and its bounded AX/OCR candidate list to the vision client, with one observation ID. Screenshots obey the existing permission/toggle. An index requires that same observation ID; visual prose alone is not a clickable target.
  `act_on_screen` defaults to **one action**. Workflows require an explicit list of at most six steps; whether each step counts as done is decided by code from that step's completion policy (see [Step completion truth table](step-completion.md)), never by the model. Exact names and location constraints restrict the candidate set before model selection; a missing named target gets one re-observation, not an unrelated substitute. Supported primitives are click/double-click/right-click, open_app, type, press_key, shortcut and scroll, all through the existing engine. Typing requires a named, already-focused field and complete text.
  A top-level pointer request may omit `action` only when it carries an explicit pointer constraint (`target_label`, `index`+`observation_id`, `region`, or `anchor_label`+`relation`); a bare goal is rejected as incomplete rather than defaulting to click. In that narrow case JEV chooses click/double-click/right-click. Explicit actions and every workflow-step action are locked and cannot be overridden by JEV.
  Literal spatial wording remains code-owned even when the realtime model emits a conflicting mouse action. For top-level Chinese requests, `右边/右侧/右方` and `左边/左侧/左方` restore the corresponding horizontal region. If the model confuses `右边` with `right_click`, the action is corrected to ordinary click unless the preserved goal explicitly contains `右键`、`右击`、`上下文菜单` or an English right-click/context-menu equivalent. Never apply this correction to an explicit right-click request.
  `new`, `resume` and `correct` distinguish task intent. Current and historical actions are separate; verified progress is recorded even if interruption arrives before the receipt. Explicit resume cannot execute an unrelated or rejected plan. `uncertain_effect` has exactly two causes: delivery itself is `unknown`, or the step's policy is `outcome_required` and no outcome evidence ever arrived. An uncertain action is not repeated, stays out of the decision model's already-done history, and a plain resume or correction cannot switch to another candidate. The user resolves it explicitly with `uncertain_resolution`: `confirmed_succeeded` (recorded as user_confirmed: the step counts done and enters the satisfied history, but never the verified history), `confirmed_failed` (block lifts, attempt stays attempted-unverified), `retry_same` (same-goal resume, the recorded target is pinned so the retry cannot pick another candidate), or `replace_target` (with `intent=correct` and an explicit new target). Uncertain records are scoped to their task chain, so a brand-new instruction is never blocked by an older task's uncertainty.
  Normal conversation plays Realtime audio as it arrives. Session voice is configured once in `session.update`; response.create never overrides it again. Settings → 模型 offers four voices in the StepFun mode (`TipTourDefaults.StepFunConfiguration.selectableRealtimeVoices`): 温柔熟女 `wenroushunv` (default, user decision 2026-09-23 after listening to every official voice the realtime model accepts), 清纯少女 `qingchunshaonv`, 经典女声 `jingdiannvsheng`, and the user's clone `voice-tone-T3kZb9MwL2`, shown with a warning because it changed speaker between replies of one session in the voice-consistency probe. The choice is stored in UserDefaults `stepfunRealtimeVoice` (the same key `defaults write` sets for A/B tests) and applies from the next session; a stored voice outside the list is named in Settings rather than silently replaced. This superseded the earlier `linjiajiejie` default. Server VAD `energy_awakeness_threshold` defaults to the provider's 2500 and is injected at session creation from UserDefaults `stepfunVADEnergyThreshold` (1–5000) while the long end-of-speech wait is investigated, and `voice_session_starting` logs which voice a session used. Once a response emits a real tool call, any queued/spilling tool-preamble audio from that response is suppressed; the result response is not created until the original response has actually ended. After the tool result is sent, the turn waits in an awaiting-followup-created phase instead of going idle. A barge-in in that window cannot tell the pending follow-up's `response.created` from the user's next response (measured: StepFun echoes neither `response.metadata` nor a client `event_id`, and a cancelled follow-up still emits created + done(incomplete) with no audio), so the session cancels the follow-up and performs one explicit session rebuild — retiring the socket the stale follow-up lives on instead of assuming which created is which. Probe: `swift run --package-path tools/stepprobe stepprobe followup-race`. Action speech is generated from the current receipt: the same Realtime session receives a one-response exact-reading instruction, and its audio is buffered until the returned transcript matches that receipt. A mismatch is displayed but not played. If macOS stops the audio engine after an audio configuration change (observed 2026-09-25 about 0.8 s after voice processing started), the session first starts the same engine again (measured: voice processing and the tap survive, and the engine stays running), falling back to a fresh engine only if that fails; it traces `audio_configuration_changed` and `microphone_restarted` with `mode` `same_engine` or `fresh_engine`, and audio playing at that moment is dropped. On this Mac a fresh engine re-enables voice processing and is stopped again, so the fresh-engine path alone loops. More than three restarts within 30 s stop the session with a visible message (`microphone_restart_gave_up`) instead of leaving it looking live but deaf. Full duplex is the default; if a user turn that began while she was audible (or within 1.5 s after) is transcribed as her own recent words (`OwnSpeechEchoDetector`: at least 4 characters, 70% of them a verbatim run of her last ~200 voiced characters), the reply to that turn is cancelled and the session switches to half duplex until the user ends it: `HalfDuplexMicrophoneGate` sends silence instead of microphone audio while her scheduled audio is projected to be playing plus 1.5 s, so the user cannot talk over her in that session. The projection comes from scheduled audio duration, not player callbacks, so the silence always ends by itself; a session rebuild keeps the fallback, a new session starts in full duplex again. Traced as `own_echo_detected` and `response_cancel_sent` with reason `own_echo`. Rationale and alternatives: `docs/research/full-duplex-echo.md` (2026-09-25; not yet accepted on a real build). Screen questions retain four historical observations; window/input changes invalidate old reads. Voice telemetry records speech-stop→first-audio latency, an estimated barge-in latency (`barge_in_detected`: first sustained loud echo-cancelled mic buffer while she speaks → server `speech_started`; an upper bound), whether the server-reported voice matches the requested session voice, and response identity (`response_created` and `response_aborted` carry the server `response_id`, `response_aborted` also its status, and `response_cancel_sent` names the response the client believed was active when it sent an unscoped `response.cancel`), without raw audio/text by default.
- **JEV text**: Ctrl+K opens the command panel. TypeSafe's `jev-latest` classifies locally detected screen labels and locations. JEV selects click/double-click/right-click targets, not prose or pixels. It acts on the top-ranked target without minimum probability or absent-score cutoffs. Its bounded loop stops on an explicit none choice, task completion, malformed responses, cancellation, action rejection/pause/failure, or 12 actions, with a final observation after the last action.
- **Ctrl+K conversation (Stage 4, since 2026-09-25)**: when a StepFun key is readable, Ctrl+K opens a conversation with Her in any selected mode instead of the bare JEV input (`TipTour/UI/DelegationPanelView.swift`, `TipTour/Delegation/DelegationSession.swift`). `step-3.7-flash` on the Step Plan route answers in JSON mode with one of: a short reply or clarifying question, a complete draft for Claude Code, or a screen goal that is handed to the JEV loop above. She asks only about effect, trade-offs and scope, never for file paths. A draft is sent only when the user presses 「发出去」; the hand-off runs as described in [runtime.md](runtime.md) (private worktree, git readback), and every sentence about the hand-off (「交给 Claude Code 了…」, the receipt headline, merge and discard) is app-owned text built from the receipt, never model text. A say-do guard asks the model once more when it promises to act but returns neither a draft nor a screen goal. Without a StepFun key Ctrl+K stays the JEV input and still requires the JEV mode.

`stepfun` voice is the default selected mode for fresh installs (voice first, `docs/PRODUCT.md`); JEV text is the fallback entry, and an existing user's saved mode is never switched. Onboarding (since 2026-09-23, `TipTour/UI/Panel/PanelOnboardingView.swift`) is two panel steps: save the selected mode's API key (with a link to where to get one), then grant only what the first use needs (`CompanionManager.hasFirstUsePermissions`: voice needs microphone + Accessibility, because the ⌃⌥ event tap requires Accessibility; JEV needs Accessibility + Screen Recording). Screen Recording for voice is requested from the ready panel's permission rows until the in-conversation request exists. The cursor overlay starts whenever onboarding is done and Accessibility is granted. The mode picker and the name live in Settings; the ready panel (`PanelReadyView`) shows the shortcut keys (clickable, same as pressing them) and three example phrases. A key that exists but has not been read in this process (`.saved`, every relaunch) shows the ready panel, not setup; refused, undecodable, unknown or missing keys show an in-place key field with the Keychain message. The name is optional, stored in UserDefaults `companionName` (one line, ≤20 characters), editable in Settings → 模型, shown as the panel title, and placed in the StepFun session instructions via `CompanionManager.voiceSessionInstructions(companionName:)`, which the DEBUG `--voice-route-probe` also uses (`-companionName <name>` overrides it for one run). Both voice modes require microphone access. The previous onboarding flag is migrated to a new mode-setup completion flag so existing users also choose a mode. Settings → 模型 shows the selector and only the selected mode’s key input. Successful key reads are reused in process memory; settings check presence without decrypting. Keys are stored only in macOS Keychain; no environment, sibling project, or hosted-key fallback. The UI must report Keychain errors accurately.

No Claude/Hermes integration, separate Flash Lite matcher, image-generation service, recording/video pipeline, or Worker proxy is bundled. Do not reintroduce them without an explicit user request.
