# Runtime architecture

Part of the [architecture overview](README.md). Moved verbatim from `AGENTS.md` on 2026-09-23.

- `CompanionManager` persists the selected mode, gates mode-specific shortcuts, and coordinates hotkeys, provider sessions, focus highlight, permissions, and overlay state. It owns the cancellable JEV task and prevents overlapping text/voice runs.
- `TipTourEngine` is the shared facade for perception, exact targets, workflow submission, action history, and localhost harness operations. `WorkflowRunner` owns pauses, per-operation tokens, target resolution, and post-action checks. `ActionExecutor`/`TipTourActionDriver` deliver CUA input. Never bypass these boundaries.
- Delegation to Claude Code (`TipTour/Delegation/CodingAgentDelegation.swift`, Stage 4) is not desktop input and does not go through `TipTourEngine`/`WorkflowRunner`: it runs `claude -p … --output-format stream-json --permission-mode auto` in a private git worktree under `~/Library/Application Support/Her/worktrees/`, and decides the execution outcome from an independent `git diff` against the base commit, not from Claude Code's own words. A diff is evidence of changes, not proof that the user's whole request passed acceptance. Initial project discovery uses the user's most recent Claude Code session (`~/.claude/projects/*/*.jsonl` `cwd`), skipping Her's worktrees, `.claude/worktrees/`, temporary directories and Claude's scratch spaces. Each draft retains its bound project through revisions and sending rather than re-reading the latest project. The user may explicitly replace that binding through the draft's folder picker; `git rev-parse --show-toplevel` validates the selected root. A missing binding cannot silently adopt later activity, but can be recovered by an explicit selection. Merging happens only on the user's decision and only while the workspace still matches what the receipt showed (a SHA-256 of `git diff <base>` taken at readback and checked again at merge) and the project is still on the branch it was on when the workspace was made; otherwise nothing is merged and the current contents are shown as a new receipt, or the branch mismatch is named (2026-09-27). That new receipt opens with a notice saying how it differs from the one the user saw (same files with changed content, which files were added or dropped, or that a receipt restored after a restart cannot be compared), labels the tool's summary as written before the change, and keeps the notice across a restart (2026-09-28). A closing question is relayed only from prose; code spans such as `git status` output are ignored. Untracked files (for example hook output such as `.statamcp/`) are named in the receipt and notice as not going to be merged, and are never merged. They are deleted with the workspace after a merge, a discard, or a run that ends without a change (not moved to the Trash); the receipt, notice and Her's closing line say so by file name (user decision 2026-09-28: observed untracked files were tool metadata or deliberate test files, so say it rather than keep them). Hand-off records are re-read before every write, so a record the user edits or deletes by hand while Her runs stays that way; the receipt's change summary and untracked list are stored so a receipt rebuilt after a restart shows the same.
- A pending delegation change keeps its project context and merge/discard decision until resolved. Another draft is refused before displaying the model's hand-off promise. Follow-up replies, model errors, screen hand-offs and starting a new conversation do not remove that decision. This is single-pending-change protection inside the existing session, not a durable task queue or restart recovery.
- Sending enters a busy preparation phase before creating the worktree, preventing another request or conversation reset from interleaving. A preparation failure retains the same draft and project for retry. Draft entries carry the actual bound project for display; reports describe observed changes rather than overall goal completion and expose git change statistics separately from the agent summary.
- Explicit project selection enters a separate busy validation phase before awaiting Git. Invalid selections preserve the old project, draft and tool; pending changes cannot be redirected. The confirmed draft is sent verbatim after a narrow runtime prefix identifying the created worktree as the only writable copy and the original path as identification only, prohibiting writes to the original checkout, new worktrees, merging and pushing. This states the already-approved isolation contract; it is not a replacement for the CLI sandbox or independent repository readback.
- A successfully selected project also becomes the current conversation's explicit project. Later requests use the current draft first, a pending workspace second, then that explicit selection, and only otherwise discover a recent project. Execution failure, cancellation or completion does not erase the explicit choice; another valid selection replaces it and a new conversation clears it. A pending workspace still takes precedence after a conversation reset. This prevents a failed-task retry from silently returning to another project's recent activity.
- The current draft explicitly selects Claude Code, Codex, Kimi Code or Step Code (2026-09-26 approvals). Selection is bound through revisions/preparation and recorded in the receipt; busy and pending-decision sessions cannot switch tools. Claude remains the initial selection. Codex uses `codex --no-daemon -a never exec --sandbox workspace-write --json -m gpt-6-luna -c 'model_reasoning_effort="high"' -- <prompt>`. Kimi uses `kimi -p <prompt> --output-format stream-json`. Step uses `step --mode json --print --approval-mode auto --non-interactive-approval allow --no-update-check -- <prompt>`. Only Codex overrides the model/effort; the other CLIs use their existing configuration. Commands resolve through the existing login-shell launcher with separate argv values, not interpolated shell scripts. There is no automatic model/tool fallback, auth import or global configuration edit. Initial project discovery remains the Claude-session locator for all four tools; explicit folder selection corrects it. No extra CLI history reader was added.
- For the default Kimi and Step commands, if `kimi` or `step` is absent from `PATH`, the launcher resolves that same CLI at `~/.local/bin/kimi` or `~/.stepcode/bin/step`; this is executable-path lookup, not a tool fallback. Step launches in a non-interactive zsh login shell that sources the existing `~/.zshrc` when readable. It captures the CLI arguments and confirmed worktree path in read-only shell values before sourcing, then sets the working directory back to that worktree. The launch keeps the user's existing terminal proxy configuration; Her does not import credentials or change global network settings. Sourcing user startup code can have side effects.
- The confirmed-task prompt tells the CLI to report CLI/plugin-generated untracked helper files only: do not delete or commit them.
- Step's single-process automatic approval for a confirmed task was explicitly authorized after disclosing that Step lacks Codex-style system sandboxing. Kimi uses its print-mode approval policy. All tools run in the selected project's private worktree, but Git isolation and the outbound path constraint are not OS permission enforcement. Her never reads CLI credentials; the selected CLI manages its own authentication and provider routing. Step's normal extensions remain enabled because disabling them prevented its default OAuth/provider path in the real probe.
- `DelegationAgentOutput` normalizes the CLIs' JSONL formats. All require exit 0 plus their completion evidence: Claude's result, Codex's `turn.completed`, Kimi's final nonempty assistant message with no tool calls (a following tool call/result invalidates it), or Step's `agent_end` with a final assistant `stopReason=stop`. Kimi's trailing `session.resume_hint` supplies the session ID without overwriting the final reply. Step's session header supplies its ID; `message_end` alone is not whole-run completion, and error/aborted/length stop reasons fail. A Step tool error is a failure-detail fallback, not a permanent failure if a later valid terminal response recovers. Model claims never replace Git readback.
- Both stdout/stderr are drained while running, and launch/cancel ownership remains synchronized. Unknown Kimi/Step/Codex costs stay absent rather than being estimated. CLI internal network retries are not Her tool switches; the Step probe recovered after two internal retries. Existing cancellation, merge and untracked-file behavior is unchanged; successful CLI fixtures do not prove native acceptance or each real CLI's cancellation behavior.
- Ground exact local IDs/marks first, then AX, browser DOM/CDP, local CoreML/OCR, and finally raw `box_2d`/hint coordinates when a caller such as the localhost harness supplies them. JEV never invents coordinates and never walks stale alternative rankings after a failed action.
- A JEV run reports its end in Chinese. Its "done" is JEV's own judgement, worded as such ("这是 JEV 自己的判断，Her 没有另外核验"); a run that judges the goal met without taking any action is reported as not done. When a Ctrl+K screen goal is handed to JEV, how it ended — including not starting because another run holds the desktop — is said in the conversation and recorded in the model's transcript as app data (2026-09-27). Whether it can start (no run in progress, desktop admission, a readable JEV key) is decided before anything is shown: only a goal that started shows her reply ("正在点击…"); otherwise the panel says only 「没去点：<reason>」 (2026-09-28).
- JEV runs local detection while active without changing the user's persisted Accurate Grounding setting (Settings → 隐私 → 精准定位). Its command panel freezes position during execution; Escape/Stop cancels the task and active workflow.
- Ctrl+Shift paints a focus region; workflow plans bind to its app and text selection. It is not sent to any model (Gemini, its only recipient, was removed on 2026-09-25). Ctrl+Option+Command is a Speak/Type/Highlight input chooser, not an extra model mode.
- Auto-click controls action delivery; JEV requires auto-click. CUA's toggle gates all desktop actions. Screenshots controls remote images, not local perception. Voice needs the microphone.
- AX is enabled for Electron on app activation. Preserve batched AX reads, messaging timeouts, target app pinning, clipboard/selected-range protections, and event-driven detection refreshes.
- The perception cache retains one local image with its capture time and observation identity. Visual candidates are restricted to the target application's foreground window; whole-display OCR from other apps cannot become its controls. Window identity and bounds participate in capture invalidation; the JEV panel uses the application captured by its shortcut rather than the panel itself. AX controls are merged with OCR before ranking; secure AX fields are excluded by the AX reader. This does not redact screenshots, so the remote screenshot toggle remains important. Failed/superseded captures cannot replace newer observations. YOLO may only borrow overlapping OCR text; a highly overlapping YOLO box cannot rename the same AX control. Distinct same-name controls remain distinct.
- `DesktopTaskExecutor` adapts voice steps to the shared engine. `DesktopActionVerifier` checks selected/focused state, typed values, or a newly visible explicit result label. A driver return, changing target set, or model `done` is insufficient. Generic keyboard/scroll outcomes without a checkable result remain unconfirmed; do not market that as full workflow completion.
- `DesktopDecisionPacket` is the per-action SSOT for `intent / action / target / where / scope / confidence / perception / planning / evidence`. Exact and targetless actions create deterministic packets. Ambiguous pointer actions use JEV speculative fan-out: one request asks `action` plus `target_click`, `target_double_click`, and `target_right_click`; code consumes only the target head matching the chosen or explicitly locked action. Probability and margin are recorded but are not threshold-gated until labeled traffic exists.
- `open_app` is a targetless fast path: it uses context-only observation, never requires screenshot/OCR/JEV, resolves localized installed-app names once to a bundle ID, then reuses WorkflowRunner/ActionExecutor and verifies that the target bundle has a live process. Intermediate app activations must not cancel the atomic launch; any later step still re-pins the foreground app/window before sending input, and unrelated switches still pause other action types.
- `open_app` success means user-visible state, not merely a live process: the resolved app (including nested helper bundles) must own an on-screen top-level window and be foreground. If a background wrapper process exists with no window, LaunchServices gets one bounded reopen attempt; otherwise the receipt stays unverified and must not say the app opened.
- `describe_screen` must describe the target application's visible window, never the cursor display as a substitute. It first checks for an on-screen top-level window, captures that `SCWindow` directly, and refuses visual claims when the app has no visible window. The captured window is the focused AX window mapped to its `SCWindow` (falling back to frontmost z-order, never largest-area), and the observation is bound to that window's identity: a slow vision result is only spoken while the same window ID, frame, app and content version are still current, the capture is fresh (`DesktopObservedWindowIdentity`), AND a fresh capture of the same window still matches its dHash content fingerprint (re-verified owner PID included) — so a same-window page navigation or dialog during the call is caught and re-read once. A yes/no “can you see it?” question is answered from local window state without the remote vision round-trip. Whole-display OCR/YOLO is suppressed when the selected app has no visible window so desktop/other-app text cannot be attributed to it.
- `DesktopVoiceTrace` uses the `VoiceTask` unified-log category with status/identity metadata. Opt-in DEBUG `voiceDiagnosticTraceEnabled` writes bounded local raw diagnostics, not credentials or images. Do not enable it silently for private user sessions.
- Default pipeline events retain only hashed diagnostic IDs, statuses and counts; they do not persist the free-form message, goal, target label or typed value. Console traces for desktop actions and provider tool calls likewise omit user content. Existing log files from older builds are not rewritten by this change.
- The user approved adopting the log-window localization in commit `671d8bb`. After an Xcode GUI build, the primary agent checked Advanced → 查看日志; filtering by `listener_ready` showed 77 matching rows out of 2475. This confirms the log view/filter, not full Stage 4 acceptance.
- The localhost harness (`127.0.0.1:19474`) exposes the engine to developer clients. It rejects non-loopback `Host` headers and foreign browser `Origin` headers before routing, and caps buffered requests at 1 MiB; other local processes still have access. `/v1/agent-contract` is canonical. Preserve trace IDs, single-action workflow limits, and explicit deterministic `/v1/tasks` sequences.
- Portable app instructions live in `TipTour/Skills/**/SKILL.md`; precedence is user overrides, project skills, then bundled skills. General documentation belongs outside the app target.
